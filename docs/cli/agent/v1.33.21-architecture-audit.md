# Architectural Audit: dirgha-code v1.33.21 → gemini-cli

## 1. Executive verdict

The current resume + compaction architecture in dirgha-code is not salvageable by patching. The root mistakes—using the conversation history array as the sole source of truth, injecting synthetic user-role messages for system recovery, basing compaction decisions on cumulative token totals instead of actual history size, and splitting loop detection across two mechanisms with incompatible thresholds—cannot be fixed incrementally without introducing more regression surface. The correct path is a refactor in place that replaces the mutable `history: Message[]` with a `TaskLedger` (append-only record of all events) and derives the provider-bound `Message[]` array from a `ConversationProjection` that applies compaction, budgets, and system reminders without polluting the ledger.

Verdict: **(b) refactor in place**, with the understanding that the refactor replaces the core context management layer entirely while keeping the tool registry, slash commands, keystore, and TUI layout.

## 2. Tonight’s failure, traced to lines

### 2.1 Recovery message leaks into the conversation as user input

| Responsibility | File:Line |
|----------------|-----------|
| Synthetic user message creation | `src/kernel/agent-loop.ts:332–370` – `_recoverMinimalContext` returns a `{role:"user", content:"[System: tool history was compacted...]"}` |
| Injection point | `agent-loop.ts:464–471` – when `messagesForCall.length === 0` after orphan stripping, the synthetic user is used as the direct input |
| Model echoes it back | Gemini interprets the user-role message as real user input and may repeat it |

**Failure mode**: A recovery directive intended for the model leaks into the conversation because it is encoded as a user-role `Message`. The model cannot distinguish between a real user utterance and a system-injected recovery hint.

**Abstraction-level root cause**: The `history: Message[]` array is the only representation of what will be sent to the provider. There is no separation between (a) the underlying event log and (b) the projected conversation displayed to the model. Recovery cues must be injected as part of the projection, not as user messages in the source of truth.

### 2.2 Tool call loop not aborted after 4 identical refusals

| Responsibility | File:Line |
|----------------|-----------|
| Refusal abort threshold | `agent-loop.ts:384–385` – `REFUSAL_ABORT_THRESHOLD = 3`, tracked in `_refusalCounts` keyed by `${name}:${JSON.stringify(input)}` |
| Count update | `agent-loop.ts:1032–1037` – only incremented when `result.isError` is true |
| Loop detector not passed in Ink TUI | `src/tui/ink/App.tsx:1001–1016` – `loopDetector` omitted from `runAgentLoop` call |
| LoopDetector threshold | `src/subagents/loop-detector.ts:28` – `maxRepeatedToolCalls: 5` |

**Failure mode**: The user saw four identical `fs_ls({path:'.'})` calls before the abort should have fired. The refusal abort threshold (3) should have caught it after the third call. The fact that it didn’t suggests either (a) the tool returned `isError:false` for one of the refusals, breaking the count chain, or (b) the `_refusalAbortTriggered` check at line 788 is placed after `executeToolCalls` but before the loop’s `continue`/`break` – and a retry resets the turn index, so the check might be skipped if all tool calls in a turn returned errors and the refusal counts were updated but the check is only after `executeToolCalls` for that turn. More precisely: if the tool calls are executed, the loop appends tool results to history (line 795), then checks refusal abort (line 788), then does the defensive tail strip (line 817), then emits `turn_end` and calls `afterTurn` hook. If the refusal abort triggers, it breaks out of the outer `for` loop. But the loop may have already incremented `turnIndex` at the top, so the total calls seen by the user can exceed the threshold if multiple tool calls are in the same turn. The user observed 4 calls, which is exactly one more than threshold. That could happen if two identical refusals occurred in separate turns, then on the third turn a single tool call pushed it to 3, but that turn’s loop ends normally because the check after tool execution sees count=3 and breaks before the fourth call. But the user reports four calls total. Possibly the first two refusals happened across two turns, the third turn produced a single call that pushed to 3 and triggered abort, but the TUI may have rendered the fourth call from a previous turn before the abort took effect. This is a timing issue: the TUI’s event stream may have emitted `tool_exec_end` for the fourth call before the abort flag was read.

**Abstraction-level root cause**: Loop detection is split across two mechanisms (refusal count with a threshold of 3, LoopDetector with a threshold of 5) that are not unified and one of which is absent from the Ink TUI. The refusal mechanism only catches `isError` results; a repeating non-error but harmful pattern (e.g., a tool that always returns success but does the same thing) would never trigger the refusal abort and the LoopDetector would need at least 5 identical calls. The LoopDetector itself uses `JSON.stringify` for the key without stable key ordering (`loop-detector.ts:37–42`), giving false negatives when argument key order differs.

### 2.3 Compaction fires repeatedly, token count rises monotonically

| Responsibility | File:Line |
|----------------|-----------|
| Proactive compaction trigger | `agent-loop.ts:472–496` – checks `totals.inputTokens > contextLimit * 0.8` |
| `totals.inputTokens` is cumulative | `agent-loop.ts:719–720` – `totals.inputTokens += assembled.inputTokens` every turn |
| Compaction fallback | `src/context/compaction.ts:145–176` – when summarizer fails, `truncateLargeToolOutputs` may not reduce token count enough |
| Compaction inserts synthetic messages | `compaction.ts:160–173` – adds a user summary + assistant "Got it" pair, increasing token count |

**Failure mode**: The user’s context window is 128k, yet token count reached 303k. The proactive compaction trigger uses `totals.inputTokens`, which accumulates across all turns and only goes up. Once it crosses 0.8 * 128k = 102,400, compaction fires on **every subsequent turn**, regardless of the actual current history size. Each compaction adds the summary + acknowledgment tokens; if the summarizer fails or produces a summary as large as the compressed portion, the token count can actually increase. The loop then hits a context-length error from the provider, which triggers the auto-compaction path (`agent-loop.ts:507–540`) as well, causing a double-compaction cycle.

**Abstraction-level root cause**: No proper token budget accounting based on the current size of `history`. The cumulative total is a proxy that always grows. Compaction by summarization does not guarantee reduction; there is no invariant that compaction must reduce token count by at least X%. Additionally, there is no cooldown after a compaction attempt that did not reduce the count.

### 2.4 Silent vec extension failure

| Responsibility | File:Line |
|----------------|-----------|
| Deferred init of vec extension | `src/state/db.ts:63–84` (referenced in audit doc `docs/cli/agent/v1.33.19-audit.md` P1-6) – `setImmediate(() => loadVecExtension(db))` |

**Abstraction-level root cause**: No proper async initialization barrier between loading the extension and using it. The deferred pattern (`setImmediate`) creates a race. The timeout hides the failure instead of surfacing it to the user.

## 5. Target architecture

The core of the refactor is a **TaskLedger + ConversationProjection** model. The ledger is an append-only log of all events (user messages, assistant responses, tool calls, tool results, compaction summaries). The projection is a function that reads the ledger and produces the `Message[]` array sent to the provider, applying compaction budgets and system reminders transparently.

### 5.1 TaskLedger

```ts
type LedgerEntry =
  | { type: "user_message"; ts: number; content: string | ContentPart[] }
  | { type: "assistant_message"; ts: number; content: string | ContentPart[] }
  | { type: "tool_call"; ts: number; call: ToolCall }
  | { type: "tool_result"; ts: number; callId: string; result: ToolResult }
  | { type: "system_event"; ts: number; kind: string; data?: unknown }
  | { type: "compaction"; ts: number; summary: string; preservedCount: number };

interface TaskLedger {
  readonly id: string;
  /** Append an entry and persist to disk (await guarantees flush). */
  append(entry: LedgerEntry): Promise<void>;
  /** Return all entries in chronological order. */
  entries(): AsyncIterable<LedgerEntry>;
  /** Return a snapshot of entries that fit within a token budget. */
  snapshot(budgetTokens: number): Promise<LedgerEntry[]>;
}
```

Implementation: JSONL file with an in-memory cache. Each `append` does `await fs.appendFile`. On crash, replay reads all lines.

### 5.2 ConversationProjection

```ts
interface ProjectionWindow {
  /** Maximum tokens for the entire Message[] output. */
  budgetTokens: number;
  /** Number of recent turns to preserve in full (not compacted). */
  preserveLastTurns: number;
  /** When true, include a system-role reminder of the current task state. */
  includeTaskReminder: boolean;
}

function projectConversation(
  ledger: TaskLedger,
  window: ProjectionWindow,
  systemMessages: Message[],
): Promise<Message[]> {
  // 1. Walk ledger entries from oldest to newest.
  // 2. When a compaction entry is found, replace the summarized entries
  //    with a single user+assistant pair (summary + acknowledgment).
  // 3. Calculate token count of the partial history as we go.
  // 4. If the token count exceeds budgetTokens, stop adding entries
  //    and emit a system-reminder for the missing tail.
  // 5. Ensure the output array starts with system messages and ends
  //    with the correct role sequence (user or tool_result).
  // 6. Inject a system-role reminder (not user-role) if includeTaskReminder.
}
```

The projection is called once per turn, after any ledger appends from the previous turn. It produces the `Message[]` for the provider call. The projection **never** modifies the ledger; the ledger is the source of truth.

### 5.3 ToolResult discriminant union

```ts
type ToolResult<T = unknown> =
  | { ok: true; value: T; metadata?: Record<string, unknown> }
  | { ok: false; error: ToolError };

interface ToolError {
  type: "refusal" | "timeout" | "invalid_request" | "internal" | "fatal";
  message: string;
  retryable: boolean;
}
```

All tools must return `ok: false` with a typed error instead of `isError: boolean`. The agent loop uses the error type to decide retry or abort:

```ts
if (!result.ok) {
  if (result.error.retryable && retriesForTurn < maxRetries) {
    // retry
  } else if (result.error.type === "refusal") {
    loopGuard?.observe(call, result);
  } else if (result.error.type === "fatal") {
    stopReason = "error";
    break;
  }
}
```

### 5.4 LoopGuard

```ts
interface LoopGuard {
  observe(call: ToolCall, result: ToolResult): void;
  isLoopDetected(): boolean;
  reason(): string | null;
  reset(): void;
}

class StableLoopGuard implements LoopGuard {
  private callFrequencies = new Map<string, number>();
  private maxRepeatedCalls: number;
  private lastResultHash: string | null = null;
  private stagnationCount = 0;
  private maxStagnation: number;

  constructor(config: { maxRepeatedCalls: number; maxStagnation: number }) {
    this.maxRepeatedCalls = config.maxRepeatedCalls;
    this.maxStagnation = config.maxStagnation;
  }

  observe(call: ToolCall, result: ToolResult): void {
    // Use stable stringify for args (sorted keys).
    const key = `${call.name}:${stableStringify(call.input)}`;
    const count = (this.callFrequencies.get(key) ?? 0) + 1;
    this.callFrequencies.set(key, count);

    // Check output stagnation: hash the result content.
    const resultText = result.ok ? JSON.stringify(result.value) : result.error.message;
    const hash = simpleHash(resultText.slice(0, 500));
    if (hash === this.lastResultHash) {
      this.stagnationCount++;
    } else {
      this.stagnationCount = 0;
      this.lastResultHash = hash;
    }
  }

  isLoopDetected(): boolean {
    for (const count of this.callFrequencies.values()) {
      if (count >= this.maxRepeatedCalls) return true;
    }
    return this.stagnationCount >= this.maxStagnation;
  }

  reason(): string | null {
    for (const [key, count] of this.callFrequencies) {
      if (count >= this.maxRepeatedCalls) return `repeated call: ${key} (${count}x)`;
    }
    if (this.stagnationCount >= this.maxStagnation) {
      return `output stagnation: ${this.stagnationCount} turns with identical result`;
    }
    return null;
  }

  reset(): void {
    this.callFrequencies.clear();
    this.stagnationCount = 0;
    this.lastResultHash = null;
  }
}
```

This single guard replaces both the refusal-count map and the separate `LoopDetector` class.

### 5.5 System-reminder injection pattern

Instead of injecting a synthetic user message for recovery or task state, the `projectConversation` function appends a system-role message at the appropriate position:

```ts
if (window.includeTaskReminder) {
  const reminder: Message = {
    role: "system",
    content: "[Reminder: continue the current task. The following is the conversation history up to now. Do not restate.]"
  };
  // Insert as the last system message before the conversation history.
  // This keeps it out of the user/assistant turn sequence.
}
```

The ledger never contains this message. It is added only to the projected array.

### 5.6 Snapshot-then-resume compaction

When `projectConversation` determines that the token budget would be exceeded (based on the current ledger entries), it writes a `compaction` entry to the ledger (via `ledger.append`) before building the projection for the next provider call:

```ts
async function maybeCompactLedger(
  ledger: TaskLedger,
  budgetTokens: number,
  summarizer: Provider,
): Promise<void> {
  const entries = await collectEntries(ledger);
  const tokenCount = estimateTokens(entries);
  if (tokenCount < budgetTokens) return;

  const splitIndex = findSplitPoint(entries, budgetTokens * 0.3); // keep 30% tail
  const historical = entries.slice(0, splitIndex);
  const preserved = entries.slice(splitIndex);

  const summary = await summarize(historical, summarizer);

  // Write a compaction entry that the projection will use.
  await ledger.append({
    type: "compaction",
    ts: Date.now(),
    summary,
    preservedCount: preserved.length,
  });
}
```

The projection then:
- Replaces all entries before the compaction entry with a single user+assistant pair (summary + "Got it").
- Preserves the entries after the compaction entry.
- Calculates token count of the resulting array and verifies it is below budget. If not, it retries with a tighter split.

This approach guarantees that compaction reduces token count because the projection applies it, not the compaction function itself. The ledger remains append-only; the projection is where the transformation happens.

## 9. Open questions for the human architect

1. **Resume-after-crash: replay tool calls or re-attach to results?**  
   When the CLI crashes mid-turn, on relaunch should the system re-execute the tool calls that were in-flight, or should it prompt the user to provide the results manually? gemini-cli replays from the recording service which includes the tool results, so it never re-executes. We could do the same: the ledger's `tool_result` entries are persisted, so on resume we replay them. This avoids duplicate side effects (e.g., `fs.writeFile` running twice). The downside is that we must decide how to handle tools that were executing but hadn't returned a result before the crash – they are lost and the model will see a gap. My recommendation: do not re-execute; the ledger preserves the last complete state; the user can re-prompt.

2. **What is the acceptable cost ceiling on summarization tokens per compaction?**  
   gemini-cli uses a 1200-token budget for the state snapshot (<chatCompressionService.ts:145<, plus the verification pass which adds another ~1200 tokens). The total cost per compaction is ~2400 output tokens + input tokens for the summarization call. For dirgha, with a 128k context window, spending 2400 tokens every 20k tokens of history is acceptable (0.5% overhead). For models with 1M context (e.g., DeepSeek), we should scale the budget proportionally, maybe 5000 tokens per compaction. This needs a configurable `maxSummaryTokens` in the compaction config.

3. **Is gemini-cli's `chatCompressionService` license-compatible to study + reimplement?**  
   The provided source files are under an Apache 2.0 license (Google LLC, SPDX-License-Identifier: Apache-2.0). You can reimplement patterns from it without legal risk, as long as you do not copy verbatim. The algorithmic descriptions in this audit are already original.

4. **Should the `TaskLedger` be SQLite-backed instead of JSONL?**  
   JSONL is simple, human-readable, and survives partial writes well. SQLite would allow queries (e.g., "find the compaction snapshot for turn 300") but adds build complexity and a native dependency. Stick with JSONL for the first implementation; migrate to SQLite only if replay time becomes a problem (>10k entries).

5. **Tool output distillation vs. masking: which to implement first?**  
   Distillation (truncation + file offload) is simpler and covers the common case of large grep/file output. Masking (replacing with intent summary after the tool runs) requires an LLM call. Implement distillation first (Step 8), then consider masking as a follow-up. gemini-cli does both, but distillation alone solves the 303k token problem.

6. **What is the desired maximum number of preserved turns in the projection?**  
   gemini-cli uses 30% of history by character count (chatCompressionService.ts:61). For dirgha, we should tie this to the token budget: preserve enough recent turns to maintain conversational coherence, but no more than 40% of the budget. A concrete default: preserve the last 4 turns or 50k tokens, whichever is smaller.
